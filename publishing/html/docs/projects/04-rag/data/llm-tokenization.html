Token 与分词：文本是怎么变成数字的

为什么先讲 token

← 上一节文档开头下一节 →中英文的比例差异

模型不认识字符，只认识 token【词元】。所有价格、所有上下文窗口的限制、 所有"字符数不等于 token 数"的意外，源头都在这一层。

"Hello, world!"  →  ["Hello", ",", " world", "!"]     4 个 token
"你好世界"        →  ["你", "好", "世", "界"] 或更少   取决于词表

中英文的比例差异

← 上一节为什么先讲 token下一节 →BPE：主流分词算法在做什么

经验值（不同模型、不同词表会有出入）：

英文：1 个 token ≈ 4 个字符，常见单词基本各占 1 个
中文：1 个 token ≈ 1~1.5 个字符，常用词常被压成 1 个 token

所以「我的 prompt 有 1000 个字符」这句话没有信息量 —— 英文可能只有 250 token，中文可能已经 800 token。计费、超窗都要按 token 算。

BPE：主流分词算法在做什么

← 上一节中英文的比例差异下一节 →特殊 token

现在的模型几乎都用 BPE（Byte-Pair Encoding）或其变体：

第 0 步：把文本拆成最细的字符（含 UTF-8 字节级回退）
第 1 步：统计相邻字符对的频率，把出现最多的那对合并成一个新符号
第 2 步：重复，直到符号总数达到词表大小（如 32000 / 128000）

BPE 的好处是词表可控又能覆盖任意新词：词表里存的是常见片段而不是完整单词表， 生僻词会由若干片段拼出来，而不是被 <unk> 丢掉。

特殊 token

← 上一节BPE：主流分词算法在做什么下一节 →常见坑
[BOS] 开头标记      [EOS] / <|endoftext|> 结尾标记
[CLS] [SEP]        BERT 系的分句标记
<|vision_start|>   多模态的模态边界

对话模型的「角色标记」也是特殊 token：<|im_start|>user\n...<|im_end|>\n。 所以messages 变成 tokens 时算的是"一整段对话文本"，不是"每句话各算各的"。

常见坑

← 上一节特殊 token下一节 →文档结尾
  • 按字符数估预算，中文场景超窗报 400： 把估算规则换成「中文按 1 字 ≈ 1 token，英文 4 字符 ≈ 1 token」再估算。
  • 长文档硬截断：在句子边界截断，别从半个词中间剪开。
  • 以为 token 和字数成正比：代码、URL、数字、"……"这类字符的 token 密度非常高， 一段看似很短的代码可能吃掉几百 token。
  • 计费对账用响应里的 usage：估算只用于 sizing，最后以服务端返回的用量为准。
