向量检索与关键词检索：各自擅长什么 ==================================

RAG 检索阶段通常有两条路，把它们互补起来就是「混合检索」。

向量检索（语义路）

把 query 和文档都压成向量，用余弦相似度排序。

擅长：同义改写、跨语言语义、模糊意图（"卡住了怎么办" → "阻塞/超时"） 不擅长：精确符号（setTimeout、bge-m3、ECONNRESET、报错码）

原因不难理解：embedding 模型会把专有名词"泛化"成它训练语料里的相似分布， 符号的字面信息在这一步就被抹掉了一部分。

关键词检索（BM25 路）

经典的词频打分算法，只统计字面命中。

擅长：专有名词、函数名、报错码、身份证号、版本号 不擅长：同义改写（"删掉" 检索不到 "删除"）

为什么两路分数不能直接相加

向量相似度在 0~1，BM25 分数可能是 3.7、15.2 且没有上限， 直接加权求和等于拿米和斤做加法，关键词路会永远碾压向量路， 混合检索退化成纯 BM25。

正确做法是 RRF（Reciprocal Rank Fusion，倒数排名融合）：

RRF_score(doc) = Σ 1 / (k + rank_i)

它只吃排名不吃分数，排名天然无量纲。两路都出现的文档会拿到两份加分， 自然浮到最上面 —— 语义和关键词都认可的文档，最可能是答案。

参数经验

粗召回 fetch_k = 20 宁多勿漏，交给后面的 rerank 精排 最终 top_k = 5 太大会稀释 prompt，太小会漏答案 rerank 精排 top_n = 5 只对这 20 条逐对打分，不碰全库

常见坑

  • query 太长（用户贴了一整段报错日志）：在入口显式截断或提纯， 否则真正有用的报错码排在后面被剪没了。
  • metadata 过滤字段名写错（source 拼成 sorce）：会静默返回 0 条， 程序不报错但结果是空的，排查成本极高。
  • 查询时换了 embedding 模型：库里是老模型的向量，查询用新模型， 分数全是噪声。入库要记模型名，查询前校验一致性，换模型必须重建索引。
