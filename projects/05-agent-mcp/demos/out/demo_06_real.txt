────────────────────────────────────────────────────────────────────────
  1. 一份计划长什么样：SubTask 的四要素
────────────────────────────────────────────────────────────────────────
目标：对比两个项目的持久化方式
[ ] t1  确定要对比哪两个项目
[ ] t2  查 Project 01 怎么落盘  (等 t1:pending)
[ ] t3  查 Project 04 怎么落盘  (等 t1:pending)
[ ] t4  汇总两者的差异  (等 t2:pending, t3:pending)
进度 0/4（完成 0）

每个 SubTask 只有四样东西，但缺一不可：
  id         —— 依赖要引用它，必须唯一
  title      —— 给模型看的一句话
  depends_on —— 要等谁。**这是唯一能算出并行度的信息**
  status     —— pending/running/done/failed/skipped，推进的依据

它和 Milestone 05 的草稿纸不是一回事：
  草稿纸存**结论**（已经查到了什么）
  计划存**待办**（还要做什么、先做哪个）

────────────────────────────────────────────────────────────────────────
  2. 依赖决定能并行多少：拓扑分层
────────────────────────────────────────────────────────────────────────
  第 0 批：[t1]  （单独一步）
  第 1 批：[t2、t3]  （可并行）
  第 2 批：[t4]  （单独一步）

串行做要 4 轮，按批做只要 3 轮 —— 中间那批两个任务互不依赖。
这个信息**模型给不出来**：它在 thought 里写下的计划只是一串文字，
没有可计算的依赖边。有了显式 Plan，循环之外的代码就能求它。

反例：全串行的链 → [['a'], ['b'], ['c']]
一条依赖边都没有额外并行度，分层结果就是 3 批。

────────────────────────────────────────────────────────────────────────
  3. 成环会被拦下
────────────────────────────────────────────────────────────────────────
目标：一个自相矛盾的计划
[ ] a  先做 A  (等 b:pending)
[ ] b  先做 B  (等 a:pending)
进度 0/2（完成 0）
  拦住了：依赖无法推进（成环或依赖未满足），卡住的：a, b

人看一眼就知道 A、B 谁也先不了，但代码如果不查，
表现是「剩下的任务凑不出下一批」—— 然后静静地卡住。

另一种同类错误（依赖不存在的任务）：SubTask 't1' 依赖了不存在的 't9'。已有子任务：t1
必须**在派活之前**查：否则错误信息会变成「卡住了」，根本没法排查。

────────────────────────────────────────────────────────────────────────
  4. 上游失败会跳过下游（传递闭包）
────────────────────────────────────────────────────────────────────────
目标：对比两个项目的持久化方式
[x] t1  确定要对比哪两个项目
      → 就比 P01 和 P04
[!] t2  查 Project 01 怎么落盘  (等 t1:done)
      → 检索没有命中
[ ] t3  查 Project 04 怎么落盘  (等 t1:done)
[-] t4  汇总两者的差异  (等 t2:failed, t3:pending)
      → 上游 t2 未完成，跳过
进度 3/4（完成 1）

被跳过的：['t4']
注意 t3 仍是 pending —— 它不依赖 t2，不该被牵连。
这正是显式依赖换来的：失败的影响范围可以**精确计算**，
而不是「整个任务重来」或者「每步都重试一遍」。

────────────────────────────────────────────────────────────────────────
  5. 计划工具：让模型自己拆、自己推进
────────────────────────────────────────────────────────────────────────
三个工具共用同一份 Plan（各建各的就成了三份互不相通的计划）。

模型调用 plan_set（tasks 是一段 JSON 字符串）：
  → 计划已建立，共 4 个子任务，分 3 批执行：[t1]、[t2,t3]、[t4]。同一批内的子任务互不依赖，可以并行做。

模型写错 JSON 时（很常见），工具返回文本而不是抛异常：
  → [计划建立失败] 计划不是合法 JSON（Expecting value: line 1 column 1 (char 0)）。原文前 200 字：我觉得应该先查资料再汇总

  ↑ 注意：这次失败把上一份计划清空了。这是「整份重设」的代价，
    换来的是不会出现半新半旧的计划 —— 模型重发一次就好。

推进 t1、t2 之后，t4 会自动变成可做的：

[x] t1  确定对比对象
      → P01 与 P04
[x] t2  查 P01 落盘  (等 t1:done)
      → P01 用 JSON 文件落盘
[ ] t3  查 P04 落盘  (等 t1:done)
[ ] t4  汇总差异  (等 t2:done, t3:pending)
进度 2/4（完成 2）
