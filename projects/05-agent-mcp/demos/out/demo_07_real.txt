────────────────────────────────────────────────────────────────────────
  1. JSON-RPC 2.0 的四种消息
────────────────────────────────────────────────────────────────────────
  请求（有 id，要等回应）
    {"jsonrpc": "2.0", "id": 1, "method": "tools/list"}
  通知（**没有 id**，不等回应）
    {"jsonrpc": "2.0", "method": "notifications/initialized"}
  响应
    {"jsonrpc": "2.0", "id": 1, "result": {"tools": []}}
  错误响应
    {"jsonrpc": "2.0", "id": 1, "error": {"code": -32601, "message": "方法不存在"}}

id 是区分「请求」与「通知」的唯一依据 —— 也是并发时配对的凭据。
自己发明一套 {cmd, args} 也能跑，但这三个问题就都要自己解决一遍。

────────────────────────────────────────────────────────────────────────
  2. stdio 传输：一帧就是一行 JSON
────────────────────────────────────────────────────────────────────────
  编码后：'{"jsonrpc": "2.0", "id": 1, "result": {"text": "第一行\\n第二行"}}\n'
  换行数：1（必须是 1 —— 末尾那个）

如果手工拼字符串而不是 json.dumps，内容里的换行会把一帧切成两帧，
对端解析到第二半时直接 PARSE_ERROR，而且从日志很难看出为什么。

  '{not json'    → 不是合法 JSON：Expecting property name enclosed in double quotes: line 1 column 2 (char 1)
  '[1,2,3]'      → 消息必须是 JSON 对象，收到的是 list
  '   '          → 空行不是一帧

────────────────────────────────────────────────────────────────────────
  3. 握手三步：initialize → notify → tools/list
────────────────────────────────────────────────────────────────────────
  ① initialize（客户端声明版本）：
  请求
    {"jsonrpc": "2.0", "id": 1, "method": "initialize", "params": {"protocolVersion": "2024-11-05"}}
  响应
    {"jsonrpc": "2.0", "id": 1, "result": {"protocolVersion": "2024-11-05", "capabilities": {"tools": {"listChanged": false}}, "serverInfo": {"name": "agent-mcp-server", "version": "0.1.0"}}}

  ② notifications/initialized（单向通知，服务端不回）：
    {"jsonrpc": "2.0", "method": "notifications/initialized"}
    → 服务端返回 None（None = 不回应）

  ③ tools/list：
  响应
    {"jsonrpc": "2.0", "id": 2, "result": {"tools": [{"name": "echo", "description": "回声", "inputSchema": {"type": "object", "properties": {"text": {"type": "string"}}, "required": ["text"]}}]}}

  如果跳过 ② 会怎样 —— 试试在握手前就调 tools/list：
    {"jsonrpc": "2.0", "id": 1, "error": {"code": -32601, "message": "尚未完成 initialize，不能调用 tools/list"}}
  错误看起来像「服务端没实现这个方法」，其实只是握手没做完 —— 很误导。

────────────────────────────────────────────────────────────────────────
  4. 两类错误不能混
────────────────────────────────────────────────────────────────────────
  ① 工具执行失败 → **result 里的 isError**（这是一次正常结果，模型该换个词再查）
  
    {"jsonrpc": "2.0", "id": 2, "result": {"content": [{"type": "text", "text": "[工具执行失败] boom: 查不到"}], "isError": true}}

  ② 工具名不存在 → **JSON-RPC error**（调用方写错了，该改代码）
  
    {"jsonrpc": "2.0", "id": 3, "error": {"code": -32602, "message": "没有名为 'nope' 的工具。已注册：boom"}}

  ③ 方法不存在 → -32601
  
    {"jsonrpc": "2.0", "id": 4, "error": {"code": -32601, "message": "不支持的方法：resources/list"}}

  把 ① 写成 ② 是这里最容易犯的错：它会让模型拿不到「查不到」这个信息，
  整轮任务直接被打死 —— 和 Milestone 01 讲的「工具失败不要抛异常」是同一件事。

  顺带：② 用 -32602（参数不合法）而不是 -32603（内部错误）。
  后者会让客户端以为是服务端崩了，从而发起毫无意义的重试。

  ④ 消息形状不对也要按协议的形状回：
  
    {"jsonrpc": "2.0", "id": 1, "error": {"code": -32602, "message": "jsonrpc 必须是 '2.0'，收到 '1.0'"}}

  连续三次调用（验证 id 没有错位）：

    calculator(1+1) = 2

    · 读到空行 = 对端关了，要把 stderr 带出来才知道为什么

    {"type": "function", "function": {"name": "rag_search", "description": "在本地项目知识库里检索资料。传入一个检索词（用自然语言即可），返回最相关的若干条笔记。事实性问题的答案必须来自这里。", "parameters": {"t…

  registry 里：['calculator', 'now', 'rag_search']
  此刻 registry 和 Agent 都不知道这些工具在另一个进程 —— 这就是 MCP 要的效果。
