────────────────────────────────────────────────────────────────────────
  3b. 规模扫描：什么时候拆才划算
────────────────────────────────────────────────────────────────────────
      子任务数      单 Agent 累计        单轮最大     Workflow 累计        单轮最大
         2             398         234            1322         260
         3             702         304            1735         276  单轮峰值低 9%
         5            1520         444            2560         307  单轮峰值低 31%
         8            3272         654            3797         353  单轮峰值低 46%

  在这个规模区间内，拆开的总量还没追平，但**单轮峰值**一直更低 ——
  峰值低意味着不容易撞上下文窗口上限，这是另一个维度的收益。

  单 Agent 的第 N 轮要带着前 N-1 轮的原文，体量随步数**线性增长**；
  Worker 的每个请求只带自己的那一点，体量**基本恒定**。

  拆分的收益不是凭空来的，它来自两件事：
    ① 每个 Worker 的请求里没有别的 Worker 的检索原文（上下文隔离）
    ② 传递的是**结论**而不是原文

  代价也要说清楚：
    · Worker 之间不能直接对话，只能通过草稿纸 / Plan 传结论
    · 子任务拆得太碎，光是启动上下文就比省下的还多
  所以 PLANNER_PROMPT 里写的是「3 到 6 个子任务为宜」

  5. 失败传播：上游炸了下游怎么办
────────────────────────────────────────────────────────────────────────
目标：对比 Project 01 与 Project 04 各自怎么处理状态持久化
  ✗ t1 查 Project 01 怎么落盘  （0 步 / 0 次调用）
      → RuntimeError: 检索服务不可用
  ✓ t2 查 Project 04 怎么落盘  （3 步 / 1 次调用）
      → P04 的会话用 mkstemp+fsync+os.replace 原子写落盘，Turn 不可变。
  - t3 汇总两者差异  （0 步 / 0 次调用）
      → 上游 t1 未完成，跳过
汇总：只能基于已有结论汇总

  t1 失败 → t3（依赖它）被自动跳过，t2 不受影响。
  执行是**动态**的：每轮重新取 ready()，而不是照着开局那份批次派完 ——
  否则 t1 已经失败了，t3 照样会被派出去（这个 bug 真踩过）。
