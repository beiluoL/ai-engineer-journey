  在这个规模区间内，拆开的总量还没追平，但**单轮峰值**一直更低 ——
  峰值低意味着不容易撞上下文窗口上限，这是另一个维度的收益。

  单 Agent 的第 N 轮要带着前 N-1 轮的原文，体量随步数**线性增长**；
  Worker 的每个请求只带自己的那一点，体量**基本恒定**。

  拆分的收益不是凭空来的，它来自两件事：
    ① 每个 Worker 的请求里没有别的 Worker 的检索原文（上下文隔离）
    ② 传递的是**结论**而不是原文

  代价也要说清楚：
    · Worker 之间不能直接对话，只能通过草稿纸 / Plan 传结论
    · 子任务拆得太碎，光是启动上下文就比省下的还多
  所以 PLANNER_PROMPT 里写的是「3 到 6 个子任务为宜」

汇总：# Project 01 与 Project 04 的状态持久化对比

## Project 01：没有落盘机制

Project 01 的两个版本都不做任何状态持久化：

- **p01-cli** 是用 Python 标准库 argparse 搭起来的单轮问答 CLI：循环读 stdin、回车即退出、零第三方依赖，全程不保存会话历史。
- **p01-refactor** 只是把领域逻辑收进 `assistant/` 包，`main.py` 只负责参数解析与退出码，同样不涉及持久化。

也就是说，Project 01 每次运行都是"从零开始"，进程结束即遗忘，没有任何写盘动作。

## Project 04：有落盘机制

Project 04 的会话与多轮（p04-session）实现了真正的状态持久化，核心是 **mkstemp + fsync + os.replace 的原子写**：

1. 先把会话历史写进一个临时文件（mkstemp）；
2. 用 fsync 把数据刷到磁盘；
3. 再用 os.replace 原子地替换目标文件。

这样即使写到一半崩溃，也不会留下损坏的会话文件——要么是旧的完整版本，要么是新的完整版本。

配套的两个设计事实：
- 会话中的 **Turn 是不可变的**；
- 恢复历史后拼进 prompt 的顺序是 **system → 历史 → 本次提问**。

## 差异小结

| | Project 01 | Project 04 |
|---|---|---|
| 是否落盘 | 否 | 是 |
| 会话历史 | 不保存 | 持久化到磁盘 |
| 写入方式 | — | mkstemp + fsync + os.replace 原子写 |
| 崩溃安全性 | 不适用 | 原子替换，避免半写损坏 |

一句话概括：**落盘能力只存在于 p04-session，Project 01 的两个版本（p01-cli、p01-refactor）均无。**
