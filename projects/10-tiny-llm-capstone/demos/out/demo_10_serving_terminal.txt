
==============================================================================
  M10 · Serving：OpenAI 兼容接口 / SSE 流式 / 健康检查 / 并发压测
==============================================================================

── 1. 服务配置 ───────────────────────────────────────────────────────────────────
  绑定地址                                 127.0.0.1:端口由操作系统分配（port=0）
  为什么用 port=0                          测试与 demo 永不撞端口，CI 上也不会随机失败
  max_tokens                           32
  压测并发                                 4
  协议                                   OpenAI 兼容：POST /v1/chat/completions、GET /health、GET /metrics

── 2. 请求体（OpenAI 兼容形状） ───────────────────────────────────────────────────────
  {"model": "tiny-llm", "messages": [{"role": "user", "content": "问：什么是 LoRA？答："}], "max_tokens": 16, "temperature": 0.0, "stream": false}
  为什么照抄这个形状                            任何 OpenAI SDK / 前端都能无改造接上，省掉一层适配

── 3. 起服务 ────────────────────────────────────────────────────────────────────
  base_url                             http://127.0.0.1:51421
  线程数                                  1（标准库 http.server + 线程化处理）

── 4. 健康检查 / 指标端点 ────────────────────────────────────────────────────────────
  GET /health 状态码                      200
  GET /health 响应                       {"status": "ok"}
  GET /metrics 状态码                     200
  GET /metrics 字段                      errors, generated_tokens, mean_latency_ms, p50_latency_ms, p95_latency_ms, requests, throughput_tokens_per_sec
  此刻的数值                                全 0 —— 还没发过请求（见第 10 节打完流量后的读数）
  为什么要 P95 而不是平均值                      平均值会被大量快请求稀释，尾延迟才是用户体验

── 5. 非流式对话 + usage 计量 ───────────────────────────────────────────────────────
  HTTP 状态码                             200
  finish_reason                        length
  content                              '-个答：什么是 token token token token token '
  usage                                {"prompt_tokens": 21, "completion_tokens": 16, "total_tokens": 37}
  为什么 usage 必须准                        计费、限流、成本核算全依赖它，差一个 token 都是账目问题

── 6. 流式（SSE）：逐 token 交付 + 末尾 usage ──────────────────────────────────────────
  HTTP 状态码                             200
  总事件数                                 19
  含内容的 delta 事件数                       16
  含 usage 的事件数                         1   stream_options.include_usage 打开时才有
  是否收到 [DONE] 结束标记                     True
  事件拼起来 = 完整答案                         '-个答：什么是 token token token token token '
  event 1: data: {"content": "-"}
  event 2: data: {"content": "个"}
  event 3: data: {"content": "答"}
  event 4: data: {"content": "："}
  event 5: data: {"content": "什么是"}

── 7. 错误路径：非法参数必须返回 4xx，而不是 500 ──────────────────────────────────────────────
  max_tokens=0 的状态码                    400
  错误体                                  {"error": {"message": "max_tokens 必须大于 0", "type": "invalid_request_error"}}
  为什么要测这个                              错误被吞成 500，前端就没法区分「我传错了」和「服务挂了」

── 8. 一键冒烟：health → 非流式 → 流式 → 错误码 ───────────────────────────────────────────
  health 状态码                           200
  非流式状态码                               200
  流式 token 事件 / usage 事件               8 / 1
  流式是否有 [DONE]                         True
  非法参数状态码                              400
  冒烟是否整体通过                             True   四项全过才算服务可用

── 9. 并发压测 ───────────────────────────────────────────────────────────────────
  并发 1：请求 / 成功                         6 / 6
    墙钟 / 单请求（顺序）                       65 ms / 11 ms
    吞吐                                 91.60 req/s  2931.4 tok/s

  并发 4：请求 / 成功                         6 / 6

── 10. 打完流量后的运行指标 ────────────────────────────────────────────────────────────
  累计请求数                                20
  累计生成 token                           496
  错误数（含被正确拒绝的 400）                     2
  平均延迟                                 8.14 ms
  P50 延迟                               5.41 ms
  P95 延迟                               22.88 ms
  平均 vs P95                            8.14 ms vs 22.88 ms   平均值被快请求稀释，尾延迟才是用户体验

── 关键数字 ──────────────────────────────────────────────────────────────────────
  冒烟四项                                 health=200 非流式=200 流式=200 错误=400
  流式事件                                 16 个 delta + 1 个 usage + [DONE]
  并发 4 吞吐                              130.60 req/s（6/6 成功）
  一句话结论                                服务化的验收标准不是「能返回」，而是「四项冒烟 + 压测都过」
